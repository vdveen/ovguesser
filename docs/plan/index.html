OVGuesser rebuild plan

What went wrong in the Replit version, what I'd build instead, how runs get stored in the player's browser, and how it deploys to Railway. There's a working prototype in the middle of this page.

The old game was fun and the design ideas were good. It broke for reasons that come from its architecture: a server that kept game state for every player, a key-value store with a 5,000-key cap, and scoring code that lived in two places and disagreed. The rebuild moves the whole game into the browser, stores each player's runs in their own IndexedDB, and turns the server into a small static file host on Railway.

Plan in one list:

  1. Keep what worked: the NS station sign, Dutch copy, five stations per run, 5,000 points per station, grey railway lines on a map without labels, reveal for 0 points, share with a toast.
  2. Put the game logic in plain TypeScript functions with unit tests. One scoring function, used everywhere.
  3. Ship station data as a static file. The browser computes distances; nothing waits on a server between clicks.
  4. Store runs in IndexedDB, one record per run, written after every guess. Reloads resume the run. History, stats, export and import come with it.
  5. Deploy one small Node service on Railway with a health check. No database in version 1. Global stats are an optional later phase.

The storage problem, and why it doesn't come back

The storage you ran out of wasn't in the browser. It was Replit Database on the server, which caps an app at 5,000 keys. The old design wrote a key for every finished round and every session, for every player, forever. At a few hundred players a day that cap arrives within days. The fix at the time was a job that deleted old results once 4,500 keys existed.

Before

Every player's game state went to one shared server store. Writes grew with total players × rounds. Reads listed all keys. The limit was global, so one busy day could stop new sessions for everybody.

After

Each player's runs live in their own browser's IndexedDB. The server stores nothing per player. Storage grows only with how much one person plays: about 1 kB per run, so 10 runs a day for five years is roughly 18 MB. Browsers allow each site hundreds of megabytes or more. Headless Chromium on this VM reported 2,048 MB.

The browser does bring its own risks. Browsers may clear a site's data, Safari especially, and players switch devices. The Storing runs section covers how the rebuild deals with that.

Architecture

Browser · installable PWA

  • game/ plain TypeScript: distance, scoring, seeded station picks, a reducer for the round flow. No React, fully unit tested.
  • map/ MapLibre GL wrapper: basemap with labels and railways stripped out, our own railway layer, guess and station markers.
  • storage/ IndexedDB repository through idb, zod schemas, migrations, export and import.
  • ui/ React screens: start sheet, HUD, round card, end sheet, history drawer.
  • Static data, built at deploy time: stations.json (7 kB gzipped), rails.json (200 kB gzipped).

Railway · one service

  • Node + Hono, about 80 lines
  • Hashed assets with immutable caching and precompressed brotli
  • SPA fallback only for page navigations. A missing file returns 404, never index.html.
  • GET /healthz for Railway's health check
  • Later, optional: POST /api/results to Railway Postgres

External

  • OpenFreeMap vector tiles (positron style), free, no API key
  • Fallback if they go down: self-hosted Protomaps extract of the Netherlands in a Railway bucket

Stations may have opened or been renamed since September 2023, so the build script also reads an overrides.json for additions, renames and exclusions. Checking that list against the current NS map is part of phase 0. The build step turns the CSV into a 29 kB JSON file (7 kB gzipped). No database.

Railway lines

The two files you added to the root are the same 16,033 OSM ways. spoorlijnen.geojson is the tagged version of the old spoorlijnen2.geojson, with simplified geometry (36k points). export(3).geojson is the raw Overpass export at full resolution (169k points). The tags let us style and filter the lines:

  • Drop crossovers, industrial, military and test track: 979 segments that only add clutter.
  • Draw main lines thicker than branch lines. Show heritage lines (Hoorn–Medemblik, Apeldoorn–Dieren, STAR) as thin dashed lines, because they are real landmarks but no NS station sits on them.
  • Round coordinates to 5 decimals (about 1 m) and keep a single-letter usage property.

Result: 2.0 MB raw, 200 kB gzipped, down from 2.8 MB with no compression configured. docs/plan/prep-data.py already does this; it becomes scripts/build-data.ts. I'd keep only spoorlijnen.geojson in git, gzipped (1 MB), and document the Overpass query instead of committing the 26 MB raw export.

Rules and scoring

The core loop stays: a station name, you click the map, you see how far off you were, you try again until you're within 500 m or give up. Five stations per run.

Proposed round score

  • Every round starts at 5,000.
  • Every miss costs 250 + 7.5 points per km off, capped at 1,000 per miss. A 100 km miss costs 1,000, a 10 km miss 325, a 2 km miss 265.
  • A hit within 500 m ends the round and keeps what's left. First-try hits score 5,000.
  • Giving up scores 0. If the score reaches 0 the round ends by itself and shows the station, so nobody gets stuck on a 15-attempt round like Ravenstein in the old log.

The score only ever goes down within a round, and every guess counts, which is what you described in a1969d1 and b371a60. The numbers are easy to tune: they are two constants in one tested function.

Storing runs locally

This is the main upgrade you asked for. The rules I'd hold the design to:

  1. One record per run. Not per guess or per round. A finished run is about 1 kB. No counters, no key scanning.
  2. Write after every guess. The whole run record is rewritten, which is cheap at 1 kB. A reload, crash or closed tab resumes where you were.
  3. Derive, don't store, statistics. Totals, bests, averages and streaks are computed from the runs. Reading 5,000 runs takes tens of milliseconds, and cached aggregates can come later if that ever becomes slow.
  4. Storage failures never stop the game. Every write is caught. If IndexedDB is unavailable or full, the run continues in memory with a clear notice and an export button.
  5. The player owns the data. Export to a JSON file, import on another device. Import is idempotent: the same run ID overwrites, so importing twice is harmless.

Schema

// IndexedDB "ovguesser", version 1
// store "runs": keyPath "id", indexes: startedAt, status, [mode, dateKey]
// store "meta": key/value for schema version, settings, lastExportAt

type Guess = [lat: number, lng: number, distanceM: number, msIntoRound: number];

interface Round {
  code: string;            // NS station code, e.g. "UT"
  name: string;            // name at the time, so history survives data updates
  startedAt: number | null;
  guesses: Guess[];
  outcome: "found" | "revealed" | null;
}

interface Run {
  id: string;              // crypto.randomUUID()
  v: 1;                    // record schema version, migrated on read
  dataVersion: string;     // which stations.json the run was played with
  mode: "classic" | "daily";
  pool: "all" | "major";
  seed: number;            // replays the same five stations
  dateKey: string;         // "2026-09-26", Europe/Amsterdam
  status: "active" | "finished" | "abandoned";
  current: number;         // round index
  rounds: Round[];         // always 5
  startedAt: number;
  finishedAt: number | null;
  total?: number;          // cached on finish; recomputable from rounds
}

Guesses are stored as small arrays, not objects, to keep records compact. Scores are never stored per round. They're recomputed with the scoring function, so a formula change can't produce two versions of the truth again. The one exception is the cached total for fast lists.

UX and polish

Playing

  • Tap drops a pin, then "Gok hier" or Enter confirms. On phones this stops a pan from turning into a guess. Desktop players can turn on direct guessing.
  • "Warmer" or "kouder" after each miss, and chips with all distances so far.
  • At the zoom level that shows the whole country, one pixel is about 600 m, so the 500 m radius needs zooming in. After a miss under 5 km, a hint says so. The test script ran into this itself.
  • End of round: the camera fits your guesses and the station, with a dashed line from your last guess and a mini station sign.
  • Rounds and runs resume after a reload.

Feel

  • Score changes flash and show the deduction ("−322").
  • Bottom sheets on phones, cards on desktop, safe-area padding for notched phones, attribution collapsed to an ⓘ button.
  • Loading never blocks on the railway layer. If it fails, you can still play and a toast says so.
  • Share: squares per station plus attempts. Web Share on phones, clipboard and toast on desktop.
  • Self-hosted font, no Google Fonts or unpkg at runtime.

Accessibility and language

  • Keyboard: Enter confirms and continues, Escape removes the pin or closes the drawer, focus moves to the primary button when a round ends.
  • Results are announced through an aria-live region. Colour never carries meaning alone. Pinch zoom stays enabled. prefers-reduced-motion turns off animations.
  • lang="nl", all copy in one strings file so an English version is a translation job, not a refactor.

Hosting on Railway

  • One service, deployed from the GitHub repo's main branch with "Wait for CI" on, so a failing test blocks the deploy.
  • A multi-stage Dockerfile: install, run the data build, Vite build, then copy dist/ and the server into a slim Node image.
  • railway.json sets the health check path to /healthz and restart on failure. The server listens on $PORT instead of a hard-coded 5000.
  • No volume and no database in v1. It's a stateless service, so any replica serves any request, which is the property the old version lacked.
  • Pull request environments give a preview URL per branch.
  • Domains: attach ovguesser.com (seen in your error log) and ovguesser.nl (in the share text). Switch DNS only after the Railway deployment passes on its generated domain, and keep the Replit deployment running until then.

Optional later: anonymous global stats

If you want what the CSV log was trying to give you, add a Railway Postgres database and one endpoint that takes a finished run's summary: station codes, attempts, distances and score, no IP address. One row per round in one table. That gives you lines like "x% of players found Spaubeek on the first try", a hardest-stations list and a daily leaderboard. Postgres has no key cap, and a million rounds is roughly 100 MB. The game never waits on this endpoint; if it fails, the run is still saved locally. I'd only build it after v1 is live.

Decisions for you

1. Scoring

Is 250 + 7.5 per km per miss the right feel, and does the 500 m radius stay? Try a few rounds in the prototype first; the constants are easy to change.

2. Guess input

Pin and confirm by default everywhere, or direct click on desktop and pin and confirm only on touch screens? I lean towards the second.

3. Server database

v1 has none. Do you want the optional global stats and daily leaderboard in phase 5, or keep OVGuesser fully local?

4. Domains

Is ovguesser.com or ovguesser.nl the main domain, where is DNS managed, and is the Replit deployment still live?

5. Language

Dutch only, or Dutch with an English toggle from the start?

6. Station pool

Only the 395 NS stations, or also heritage stops and border stations like Emmerich or Antwerpen as a bonus mode?

7. Credit line
